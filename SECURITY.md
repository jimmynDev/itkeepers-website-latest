# Security baseline

This is a static/prerendered Astro marketing site. Browser code and generated assets must not contain credentials, API keys, private client records, monitoring data or private infrastructure details.

## Implemented
- Both the homepage consultation form and Contact form submit directly from the browser to the fixed public endpoint `https://formspree.io/f/mrppzvpo`. JavaScript sends an allowlisted FormData payload with credentials omitted and redirects rejected; native no-JavaScript submission and the explicit verification continuation POST to the same provider. The form ID is a public submission identifier, not an API secret. See `src/components/InquiryForm.astro`, `src/data/formspree.ts` and `src/scripts/contact-form.ts`.
- Formspree processes inquiries and may retain provider/archive copies before email delivery to the temporary administrator-managed inbox disclosed in the preview notice. Approved direct email/telephone links are fallback contact options; normal forms no longer compose a mailto message. No inquiry values are written to application browser storage by the contact controller.
- Client field limits, the payload allowlist, honeypot and CSP do not prove provider-side schema/body limits, spam/challenge enforcement, quotas, destination ownership or delivery. These require sanitized account-owner evidence. Recognized AJAX acceptance is distinct from inbox delivery and appointment scheduling. A browser timeout or native return does not prove rejection/cancellation; check before resending.
- `CONTACT_VALIDATION_ENABLED=false` and `CONTACT_DELIVERY_ENABLED=false` govern only the separate first-party preparation. RC/staging reject both local inquiry APIs; the production-preparation router selects non-storing `handleContact`, not the retained email-delivery function. These switches, Turnstile checks and Durable Object quotas do **not** disable or protect direct Formspree submissions. Optional legacy backend configuration is not the active form path. No secrets belong in public environment variables.
- CSP limits scripts/fonts to self, AJAX connections to self plus the exact Formspree endpoint, and native form destinations to self plus the Formspree origin. Frames, workers, objects and base elements are blocked. Inline styles remain permitted for existing SVG artwork/animations; inline JavaScript and eval are not permitted. Earlier Report-Only/browser checks are historical, not fresh validation of this proposal.
- The proposed shared RC/staging Worker policy is `strict-origin-when-cross-origin`, matching `public/_headers`. It sends only the origin on cross-origin HTTPS requests, omits the referrer on HTTPS-to-HTTP downgrade, and retains full referrer detail on same-origin requests. It replaces the former Worker `no-referrer` override, which is incompatible with Formspree Referer-based domain restriction when that setting is enabled. This is a local, unexecuted proposal; current hosted response policy has not been rechecked. Sensitive JSON replies from the dormant first-party API retain `no-referrer` independently.
- `.env*` and Wrangler `.dev.vars*` files are ignored. `python scripts/audit-security.py dist` checks repository files and generated output with bounded credential patterns without echoing matches.
- No third-party analytics, embeds, trackers or remote scripts.

## Deployment checks

Static `_headers` does not establish the policy of Worker-generated responses; verify the shared handler and actual released responses separately. The currently approved competition RC/staging are public by design. RC adds blanket noindex; staging retains its separate indexing holds. Noindex and exact-host checks are not authentication. Any future private preview requires verified access protection on every permitted hostname. See `docs/FORM_INQUIRY_RUNBOOK.md` for the operational boundary and remaining provider checks.
HSTS is staged at `max-age=86400` on `itkeepers.com` only, after read-only verification of the apex HTTPS response. It does not include subdomains or preload. The header matches in the local Workers runtime; browser enforcement over production HTTPS remains a release check. A browser can retain this policy for one day after receipt; removing the header does not immediately clear it. The live legacy site currently does not return HSTS or the new application security headers.

## Inquiry incident containment

Follow `docs/FORM_INQUIRY_RUNBOOK.md`. Agent03 coordinates the Formspree/inbox owner and Workflow. First-party flags and disabling email notifications are not a provider collection kill switch; a frontend rollback/removal alone does not stop a cached/direct public-endpoint submission. Confirm a provider-enforced stop/restriction supported by the actual account before treating collection as contained. Preserve sanitized outcome references, reconcile accepted/uncertain copies and keep approved email/telephone fallback available. Account changes, deployments and real submissions require their own authorization; none occurred in this follow-up.

Formspree documents `strict-origin-when-cross-origin` as the strictest policy compatible with its domain restriction: https://help.formspree.io/articles/form-and-project-settings/restrict-to-domain . Referer can be absent in privacy-focused browsers or forged by non-browser clients; domain filtering is not authentication or a substitute for spam/rate protection. Cloudflare response-header scope: https://developers.cloudflare.com/workers/static-assets/headers/ .
